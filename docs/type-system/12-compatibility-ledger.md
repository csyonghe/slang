# Compatibility and completeness ledger

This ledger is the bridge between the current compiler and the normative replacement design. It
prevents source behavior, generated documentation, or a redesign preference from silently becoming
a language rule.

The investigation baseline is official `master` at
`4f4ec505761e2e56a45da873d5c169ff6e512f52` (2026-07-16).

## Dispositions

| Disposition            | Meaning                                                                                   |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| **Preserve**           | Current observable behavior is accepted as normative compatibility behavior.              |
| **Preserve by mode**   | Retained only under a named language version or compatibility dialect.                    |
| **Replace**            | Current implementation representation changes while user-visible behavior is preserved.   |
| **Intentional change** | The new language rule deliberately changes observable behavior and needs migration notes. |
| **Open**               | Evidence or design review is incomplete; implementation must not choose implicitly.       |

## Required evidence before implementation freeze

For every row in the feature matrix:

1. enumerate parser entry functions and syntax registration entries;
2. enumerate all AST node kinds and standard-environment declarations involved;
3. enumerate semantic entry functions and diagnostics;
4. enumerate Core/IR mappings and any “must not reach lowering” assertions;
5. map existing positive/negative tests;
6. assign a disposition and normative rule IDs; and
7. generate missing validation cases.

The implementation may begin experimentally before every row is closed, but a replacement cannot
claim language compatibility while an `O` row lacks an explicit fallback to the old frontend.

## Known documentation/source discrepancies

These items require explicit resolution and should not be copied from generated documentation:

- lexer backslash-newline scrubbing means token spelling is not always a physical source slice;
- ordinary macro-expanded tokens do not retain a full expansion-origin chain;
- unterminated block-comment behavior in source does not currently match the language-reference
  diagnostic claim directly; and
- several generated design documents declare that they may drift from source.

The new lossless token model deliberately fixes the first two representation gaps. User-visible
lexical diagnostics still need compatibility decisions in chapter 2.
